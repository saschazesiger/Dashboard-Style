# Plan: Dashboard-Style 3.0

**Status:** draft for the owner's approval (2026-11-03). Nothing in it is built yet. Branch: `next`.

3.0 is a rewrite. It keeps what made 2.x good: tokens on `.ds-theme`, cascade layers, one motion scheme, state
layers, forced colours, the test discipline, plain CSS and dependency-free JS. It changes the parts that limit growth:
the file layout, the loading model, the options model, the JS structure and the theming model. Then it adds about 170
components, patterns and page templates.

Owner decisions of 2026-11-03, which this plan takes as given:

| # | Decision |
|---|---|
| D1 | A complete rebuild with a new API is allowed. Everything may break; a migration tool and guide replace compatibility. |
| D2 | Pages load only what they use: minified builds, a component manifest, and a bundle tool that scans a project and writes its bundle. |
| D3 | Every component group goes in: chat and AI, content, data grid, charts, forms, navigation and structure, people and media, page patterns, layout utilities, **plus everything comparable systems offer that fits an admin console** (research of 2026-11-03, below). |
| D4 | Options: variants per component, density levels per container, shape and type scales, a theme generator from one seed, declarative initialisation (`DS.init()`), a thin React adapter. Not chosen: an i18n pack and right-to-left. |
| D5 | The browser floor rises to Baseline 2024 (precise floor: [Browser floor](#browser-floor)). |
| D6 | The projects are not migrated as part of this work. |
| D7 | Plan first; build after approval, in phases with commits. |

Second round, the same day, on this plan's open questions:

| # | Decision |
|---|---|
| D8 | Projects are protected by R1: a `v2` branch, and each project's nightly tracks it before `next` merges into `main`. |
| D9 | The floor is Safari 17.5, Chrome/Edge 123, Firefox 130. |
| D10 | A destructive confirmation may use a filled button in the error tone (only in the confirm dialog and the type-to-confirm pattern; pages keep no red buttons). |
| D11 | Actions follow `--ds-shape`: a square theme has square actions, the default stays the pill. |
| D12 | `lightningcss` minifies, as a dev dependency of the build. The shipped `dist/` and tools stay dependency-free. |
| D13 | Code is highlighted by the system's own small tokenizers (about ten languages), with a hook for an external highlighter. |
| D14 | Named motion exceptions: chart lines and areas morph their path to new data, the tour spotlight glides between targets, the carousel slides. All three run on tokens, continue from their current state when interrupted, and get Motion Lab demos. |

## Release and protecting the projects

Every project's nightly workflow vendors `main` of this repository. It does so without review, and the commit to vendor
is hard-coded as `main` in each project's `update-dashboard-style.yml`. A 3.0 on `main` would therefore reach every
project within 24 hours and break it, and D6 says the projects are not migrated now.

- 3.0 is built on `next`. `main` stays 2.x and takes only fixes (2.1.x, 2.2 if ever needed) for as long as projects
  are on 2.x.
- Merging `next` into `main` is a separate, explicit owner decision. Before it happens, one of two things is true:
  - (R1, recommended) a `v2` branch exists, and every project's nightly tracks `v2`. That is a one-line change per
    project (`commits/main` → `commits/v2`, the vendor ref), which the owner approves when the time comes. After the
    merge, a project moves to 3.0 by switching its nightly back to `main` together with its own migration.
  - (R2) every project is migrated in the same step.
- `templates/update-dashboard-style.yml` gets a `REF` input (default `main`), so pinning a major is a setting and not
  an edit. It must ship in a 2.x release on `main` **before** the merge, because projects copy the template from
  there.
- Fixes that land on `main` while 3.0 is built are ported to `next` in the same session: same commit title, plus a
  note in the 3.0 changelog draft when the ported code differs.
- GitHub Pages deploys only from `main`. For the owner's review in phase 5, `site.sh` builds `next` into a preview,
  either a second Pages environment or a local `_site` that opens from disk.
- `VERSION` in a vendored copy already records the commit. 3.0 adds `major: 3`, so `check-project` can say "this
  project's config is for 2.x".

## Browser floor

"Baseline 2024" taken literally (Safari 17.4, Chrome 123, Firefox 128) misses several features by one release. The
floor is therefore **Safari 17.5, Chrome/Edge 123, Firefox 130** (D9). All three shipped by September 2024, and
iPhones on iOS 17.5 or later qualify (iOS 17 runs on everything from the iPhone XS, 2018). Final versions are checked
against `web-features` before phase 0 ends.

| At the floor (used directly) | Progressive only (behind `@supports` / feature detection, with a named fallback) |
|---|---|
| CSS nesting (allowed for projects; `src/` stays flat, below), `:has()`, container size queries, `@property`, `color-mix()`, `oklch()`, `light-dark()` (colours only), `@starting-style`, `transition-behavior: allow-discrete`, `popover`, `<dialog>`, `inert`, `details[name]` (exclusive accordions), `text-wrap: balance`, `:user-invalid`, subgrid, `linear()`, `Promise.withResolvers`, Set methods, `structuredClone` | relative colour syntax (Safari 18; used only for the live theme preview), anchor positioning, View Transitions (same and cross document), scroll-driven animations, `interpolate-size`, `::details-content`, `field-sizing`, `text-wrap: pretty`, style queries, `@scope`, `closedby`, invoker commands (`command` / `commandfor`), `appearance: base-select`, `moveBefore()`, Navigation API, iterator helpers, `sibling-index()` |

What the floor buys:
- `linear()` springs need no hand fallback, and `@starting-style` entrances need no keyframe twin.
- `light-dark()` lets one theme file carry both colour schemes. It takes colours only, so shadows and other non-colour
  values still switch through `[data-ds-scheme]` rules.
- `details[name]` gives exclusive accordions without JS.
- The `popover` attribute gives the top layer.

What it does not change:
- **Popovers stay `popover="manual"`, and closing stays in JS.** The 2.x overlay contract is the reason:
  - `popover="auto"` light-dismisses on pointerdown and lets that click reach the page.
  - It closes the other auto popovers, which bypasses the dismiss guard.
  - It handles Escape before the page's own handlers do.
  - Firefox has no `overlay` property, so CSS alone cannot keep an exit in the top layer.
- **`src/` stays flat CSS, without nesting.** The tooling reads flat CSS: `css-scan.mjs`, the `restyle` rule,
  `tokens.json`, and the `css.test.js` rules such as "hover only inside `@media (hover: hover)`". Nested selector
  lists would also raise specificity through `:is()`. A nesting-aware parser is not worth what it costs.

The "Progressive:" header notes stay, and stay tested. The browser `fallback` project of the Playwright harness is
redefined at the new floor: Chromium as the engine, with the progressive features of the right-hand column stripped
or rejected.

## What stays, what changes

**Stays** (the non-negotiables of 2.x, carried into the 3.0 AGENTS.md):
- Tokens on `.ds-theme`, never `:root`.
- The `ds-` prefix.
- Cascade layers.
- No literals in components.
- One motion scheme that themes cannot change.
- State layers, the focus ring and the disabled model.
- Overlays through one contract.
- Status never by colour alone.
- Forced colours.
- WCAG AA text.
- Field text 16px on phones.
- Labels above fields.
- `morphHtml` instead of `innerHTML`.
- Deterministic, committed `dist/`.

**Changes:**

| 2.x | 3.0 | Why |
|---|---|---|
| `src/components/<name>.css` (one file each, docs in a 3,600-line `docs/components.md`, demos in a 3,500-line `styleguide.js`) | `src/components/<name>/` holds `<name>.css`, an optional `<name>.js`, `<name>.md`, `<name>.demo.js`, `<name>.test.js` and `meta.json` | Colocation: a component is one folder, so parallel work never collides. The manifest, docs index and styleguide are generated. |
| `ds.css` with everything, 731 KB, 165 KB gzip | `ds.min.css` (about 50 KB gzip today, more with 3.0's catalogue), per-component minified files, a manifest and a project bundle | D2 |
| 6 JS modules, 590 KB together; `overlay.js` alone 190 KB | `core` (registry, init, events, config), `motion`, `dom`, `overlay` (stack, focus, dismiss, position) plus one behaviour module per component (`dialog`, `menu`, `toast`, `tooltip`, `combobox` …) | A page that has no menu loads no menu code. |
| Each project wires tooltips, ripple, menus and copy by hand | `data-ds-*` attributes plus `DS.init()` (delegation, one observer) | D4 |
| Options as scattered hooks and the 27 restyle exceptions the projects hold | A uniform size, tone, variant, density and shape model on every component; the exceptions become documented options | D4 |
| A theme sets each colour role by hand | Seed tokens → generated palette → roles → hooks; a generator for light, dark and contrast | D4 |
| `tokens.json` (own format) | `tokens.json` plus `tokens.dtcg.json` (W3C DTCG 2025.10) | Tooling |
| Deprecated 2.x names | Removed; `deprecations.json` keeps them with `removed: "3.0.0"` and the 3.0 replacement, which the migration tool reads | D1 |

The 39 components of 2.x are not deleted and re-invented. Each is ported into the new layout and options model. Its
look and motion stay where nothing argues for a change, so the tests and screenshots of 2.x stay a reference.

## Architecture

```
src/
  core/                tokens.css (scales, seeds, roles), base.css, motion.css, layers.css, utilities/
  components/<name>/   <name>.css · <name>.js? · <name>.md · <name>.demo.js · <name>.test.js · meta.json
  patterns/<name>/     page templates (HTML + md), no CSS of their own beyond a pattern file when needed
  js/core/             core.js (registry, DS.init, events, config), motion.js, dom.js, overlay.js, a11y.js,
                       position.js, format.js, store.js, hotkeys.js, virtual.js, dnd.js, chart/ (scales, axes, marks)
  icons/               one file per glyph (24px grid), plus the index
  types/               generated from meta.json where possible, hand-written where not
themes/                dark, contrast, compact, plus generated presets
scripts/               build, motion-curves, site, vendor, gen (manifest, docs index, styleguide registry)
scripts/tools/         shipped tools: bundle, theme, migrate, check-project, check-theme, verify, vite plugin
```

`meta.json` per component is the single source of truth:

```json
{
  "name": "dialog",
  "group": "overlays",
  "status": "stable",
  "classes": ["ds-dialog", "ds-dialog__head", "ds-dialog__body", "ds-dialog__foot", "ds-dialog--sm", "ds-dialog--fullscreen"],
  "attributes": ["data-ds-dialog", "data-ds-open", "data-ds-close"],
  "requires": ["button", "scrim"],
  "js": "dialog.js",
  "behaviours": ["dialog"],
  "hooks": ["--ds-dialog-width", "--ds-dialog-radius"],
  "keyframes": [],
  "icons": ["close"],
  "progressive": ["@starting-style", "closedby"]
}
```

The build checks that `meta.json` matches the CSS: every class there and no other, every hook read, every keyframe
used.

From the folders, the build then generates every file that 2.x edits by hand across components:
- `dist/manifest.json`, the docs index and the "Which component for which need" table
- the styleguide registry and the Motion Lab registry (each folder has a `<name>.lab.js`)
- the type stubs
- the hooks table of `docs/theming.md`
- the ripple host list (`meta.json` `ripple: true`)
- the keyframe and Overlays tables of `docs/motion.md`
- the icon index
- the contrast pairs of `theme-rules.mjs` (`meta.json` `pairs`)

**Keyframes** stay in one place, but that place is a generated `motion.css`: each folder holds `<name>.keyframes.css`,
and the build checks every name once, the from/to rules and the prefix. **Colour roles** a component needs are
declared in its `meta.json` with light, dark and contrast values. The build writes them into `tokens.css`,
`themes/dark.css`, `themes/contrast.css` and `themes/example.css`, so no group edits those files.

**Licences.** The HCT colour code is ported from Material Color Utilities (Apache-2.0); its notice goes into `LICENSE`,
as the Lucide and Feather notices do.

`dist/`:

| Path | What |
|---|---|
| `ds.css`, `ds.min.css` | everything, readable and minified (with a source map). Every output file, minified or single, carries the version banner |
| `ds.js`, `ds.min.js` | everything as a classic script (`window.DS`) |
| `css/core.css`, `css/components/<name>.css` (+ `.min.css`) | the single stylesheets |
| `js/core/*.js`, `js/components/<name>.js`, `js/icons/<name>.js` | ES modules, each with its `.d.ts` |
| `manifest.json` | components, dependencies, classes, attributes, JS, icons, sizes |
| `react/` | the React adapter (ES module + types), optional |
| `themes/`, `fonts/`, `tokens.json`, `tokens.dtcg.json`, `deprecations.json`, `tools/`, `LICENSE`, `SHA256SUMS` | as in 2.x, plus the generated theme presets |

**Minifying** uses `lightningcss` as a dev dependency of the build (D12), with its version pinned.
- It minifies CSS with layers, `linear()` and `@property` intact, and writes source maps. Its targets are set to the
  floor, so it never lowers or prefixes a feature.
- JS is minified by a small tested stripper: comments and indentation out, strings, template literals and regex
  literals untouched, nothing renamed.
- `dist/` and every shipped tool stay dependency-free, and `npm run build --check` stays deterministic.
- Browser tests run against the minified files, to prove they behave the same.

## Loading only what a page uses

It is possible, and the build gives three ways, from simplest to smallest:

1. **Everything, minified**: `ds.min.css` plus `ds.min.js`. No setup. This is the right default for a small internal
   app.
2. **Single files by hand**: link `css/core.css` and the `css/components/*.css` a page needs. `manifest.json` lists
   each component's dependencies, and `check-project` fails when a used class has no linked file (it does so already).
3. **Project bundle (recommended)**: `node <dest>/tools/bundle.mjs --config ds.config.json` scans the project and
   writes `ds.bundle.css`, `ds.bundle.js` and `ds.bundle.json` (a report: components, bytes, why each one is in).

How the bundle tool works:
- **Scan.** It reads the project's text files (`html`, `js`, `ts`, `jsx`, `tsx`, `vue`, `svelte`, `md`, Go templates)
  as plain text, as Tailwind does. It matches complete `ds-*` class names and `data-ds-*` attributes against
  `manifest.json`, and `DS.<module>.<fn>` and imports against the JS exports.
- **Dynamic names.** It sees only complete literals. A string like `'ds-btn--' + kind` is reported as an error that
  names the file and line. `safelist` in the config takes globs (`"ds-btn--*"`, `"component:chart"`).
- **Resolve.** Dependencies are resolved transitively: a dialog needs button and scrim, a combobox needs the overlay
  core and the listbox.
- **Cascade order.** The layer statement fixes only the order between the layers, not the source order inside
  `ds.components`. So each component gets its own sublayer, `ds.components.<name>`, and `core.css` declares every
  sublayer in manifest order.
  - Linking files by hand, a partial bundle and several per-entry bundles therefore all cascade exactly as `ds.css`
    does.
  - Layer order stays the only thing that decides; still no specificity tricks.
- **Top-level rules.** A bundle's `@property` registrations and `@font-face` rules stay at the top level. A
  `properties.css` is written next to each bundle, for widgets in a shadow root (as in 2.x).
- **Icons.** Only the glyphs the project names (`DS.icons.<name>`, `data-ds-icon="name"`) go into the bundle. Today
  every page ships all 109 glyphs; 3.0 has about 250.
- **Pages.** One bundle per project is the default. Per-entry bundles work too: `entries: { "admin": ["admin/**"] }`
  writes `ds.admin.css`.
- **Check.** `bundle.mjs --check` fails when the project's markup no longer matches its bundle, and projects run it in
  CI.
  - The nightly template does not check. It **rebuilds** the bundle from the new copy and commits copy and bundle
    together: a new vendored copy always makes the old bundle stale, so a check there would fail every night.
- **One runtime per page.** Shared state lives in a single global (`DashboardStyle.runtime`): the overlay stack, the
  scroll-lock count, the guard, the observer and the registry. Classic bundles, per-entry bundles and ES modules add
  their behaviours into it by name instead of returning early. Two bundles of the same version, or modules next to a
  bundle, therefore share one overlay stack. A browser test covers it.
- **Bundlers.** `tools/vite-plugin.mjs` (dependency-free, about 100 lines) runs the same scan on Vite's module graph
  for React and TypeScript projects. esbuild projects import the ES modules directly, and the tool prints the import
  list.

Expected sizes, as an estimate to confirm in phase 0. A typical admin page that uses about 15 components should land
around 15-25 KB gzip of CSS and 15-30 KB of JS. The 2.x page loads 165 KB of CSS and 158 KB of JS.

## Tokens and theming

Four tiers, all custom properties on `.ds-theme`:

| Tier | Prefix | Set by | Example |
|---|---|---|---|
| Seeds | `--ds-seed-*` | a theme (a handful of values) | `--ds-seed-primary: oklch(0.55 0.15 255)`, `--ds-seed-neutral`, `--ds-seed-accent`, `--ds-seed-error`, `--ds-seed-success`, `--ds-seed-warning` |
| Palette and scales | `--ds-ref-*` | the system, derived (internal, may change) | tonal steps 0-100 per seed; spacing, motion, z, state layers |
| Roles | `--ds-*` (no infix) | the system from the palette; a theme may override any | `--ds-primary`, `--ds-on-primary`, `--ds-surface-container-high`, `--ds-font-title`, `--ds-radius-card` |
| Hooks | `--ds-<component>-*` | a theme or one element | `--ds-btn-height`, `--ds-dialog-width` |

**Theme generator** (`tools/theme.mjs`, also live in the styleguide and the live tour):
- Input is one seed colour, plus optional neutral, accent and status seeds, a scheme and a contrast level.
- The scheme is one of `tonal` (default), `vibrant`, `neutral`, `fidelity` or `monochrome`, as chroma and hue presets
  over HCT tones.
- HCT is ported dependency-free from Material Color Utilities (about 400 lines), with OKLCH output.
- Output is one theme file with light, dark (`light-dark()`) and contrast values for every role, gamut-mapped. It is
  checked against the WCAG 2 pairs of `theme-rules.mjs`, and APCA is shown as advisory only.
- The styleguide's live preview runs the same JS generator. Relative colour syntax would need Safari 18, so it is
  only a progressive shortcut. The shipped file is always the generated, checked one.

**Further theme options.** Each is a single **numeric** token, and each nests, so a region can differ from the page.
The rule that makes them nest: an option is never folded into a role on `.ds-theme`. A role declared there would
resolve its `var()` on `.ds-theme`, so a nested `.ds-density-dense` would change nothing. Instead:
- The option classes set only the numeric token (`--ds-density: -2`, `--ds-size-step: -1`, `--ds-shape: 0.5`), and
  custom properties inherit.
- Each component computes at the use site, for example
  `block-size: calc(var(--ds-btn-height, 40px) + var(--ds-density) * 4px + var(--ds-size-step) * 8px)`.
- So a hook that a theme or an element sets is a base value, and density and size still apply on top of it.
  `--ds-btn-height-exact` sets a fixed height that ignores both.

| Option | Token | Values | Effect |
|---|---|---|---|
| Density | `--ds-density` | `0`, `-1`, `-2`, `-3` (classes `.ds-density-comfortable`, `-compact`, `-dense`) | control heights and paddings in 4px steps; type size unchanged. Inside `.ds-touch` and under a coarse pointer the result is clamped with `max()` to the touch minimum (44px targets): touch wins over density, and a test proves it |
| Shape | `--ds-shape` | `0` (square) to `1.5` (round), default `1` | multiplies every radius role, actions included (D11). The rest radius of an action stays `min(radius, half the height)`, so the default theme keeps pills and a square theme has square actions; the press morph scales with it |
| Size | `--ds-size-step` (classes `.ds-xs`, `.ds-sm`, `.ds-md`, `.ds-lg`, `.ds-xl`) | `-2` to `2` | height, padding, icon and type step of one control or one group |
| Scale | `--ds-scale` | `0.9` to `1.1` | type and spacing together, for kiosk or dense screens |
| Type | `--ds-seed-font`, `--ds-seed-font-mono`, `--ds-type-ratio` | font stacks, ratio of the type scale | the whole type ramp |
| Elevation | `--ds-elevation-style` | `shadow`, `tonal`, `outline` | how raised surfaces are told apart |
| Colour scheme | `color-scheme` via `.ds-theme[data-ds-scheme]` | `light`, `dark`, `auto` | one theme file serves both |

**Shipped presets** (generated, neutral names): `default`, `slate`, `ocean`, `forest`, `violet`, `amber`, `rose`,
`graphite`, each in light, dark and contrast. Plus `contrast` and `compact`.
- `compact` keeps what it does in 2.x: type at 13/18 and default heights back under a coarse pointer.
- In 3.0, `compact` is written as `--ds-density: -2` plus the type roles, so a project that loads it sees the same
  page as before.

## API conventions

One model for every component, so options are guessable:

| Concern | Form | Example |
|---|---|---|
| Component, part | `.ds-<name>`, `.ds-<name>__<part>` | `.ds-dialog__foot` |
| Variant (look) | `.ds-<name>--<variant>` | `.ds-btn--tonal`, `.ds-card--outlined` |
| Size | `.ds-sm` / `.ds-lg` … on the element or a group (sets `--ds-size`) | `<div class="ds-btn-group ds-sm">` |
| Tone (meaning) | `.ds-tone-<tone>`: `neutral`, `primary`, `info`, `success`, `warning`, `error` | `.ds-badge.ds-tone-error` |
| Density, shape | classes on any container | `<section class="ds-density-dense">` |
| State | native attributes and ARIA first (`disabled`, `aria-expanded`, `aria-current`, `aria-busy`), then `data-state` written by the system | |
| Behaviour | `data-ds-<behaviour>` with options in `data-ds-<behaviour>-<option>` or JSON in `data-ds-config` | `<button data-ds-copy="#token">` |
| Hooks | `--ds-<name>-<property>` with a fallback | `var(--ds-dialog-width, 560px)` |

A name is renamed only where 2.x was inconsistent. The 2.x → 3.0 map lives in `deprecations.json`, and the migration
tool reads it.

## JS: core, behaviours, declarative init

- **`core.js`:**
  - `DS.init(root = document, { observe = true })` attaches every behaviour whose attributes are present.
  - Delegated behaviours (ripple, tooltips, copy, hotkeys, open/close triggers) are one listener on the root and need
    no per-element work.
  - Stateful widgets (combobox, data grid, tree, chart, date picker) get a controller per element from a `WeakMap`:
    `DS.get(el)` returns it, and it has `.destroy()`.
  - One `MutationObserver` initialises added elements and destroys removed ones.
    - It watches `childList` and `subtree`, plus `attributes` filtered to the behaviour attributes. `morphHtml` patches
      in place, so a new or changed `data-ds-*` attribute arrives without any childList record.
    - Records are batched to a microtask. At the flush, only nodes that are **still disconnected** are destroyed. A
      keyed reorder without `moveBefore()` (Firefox and Safari at the floor) arrives as a remove plus an add, and keeps
      its controller.
  - `DS.init` is idempotent.
  - It always installs the **action guard** and the ripple delegation, as part of core in every bundle. A bundle can
    therefore never leave `aria-disabled`, busy or done actions clickable.
- **Controllers** share one shape: `get()` / `set()` for the value or state, `on(event, fn)` returning an unsubscribe,
  and `destroy()`. They support controlled and uncontrolled use (`data-ds-value` versus the page calling `set`).
- **Events** are DOM `CustomEvent`s with the `ds:` prefix, and they bubble: `ds:open`, `ds:close`, `ds:change`,
  `ds:select`, `ds:sort`, `ds:filter`.
  - A `ds:before-*` event is cancelable only where cancelling cannot trap someone: `before-close` of a dialog with
    unsaved changes yes, Escape no. This keeps the 2.x rule.
- **Config:** `DS.config({ locale, strings, motion, positioning })`.
  - `strings` holds the system's own few texts ("Close", "Copy", "Copied", "Show more", "Clear") in English by default.
    A page can override them; there is no language pack (D4).
  - `locale` defaults to `<html lang>` and drives the `Intl` formatters.
- **Core helpers** (each documented and tested, each optional in the bundle):
  - `a11y`: focus trap, roving tabindex, typeahead, live announcer, `inert` stack.
  - `position`: anchor positioning where supported, otherwise a small flip/shift/size placer with collision padding,
    arrow and offset.
  - `format`: number, bytes, duration, relative time with one shared ticking clock, list and plural.
  - `store`: remembered UI preferences in `localStorage` under a namespace, such as columns, density, dismissed
    banners and sheet widths.
  - `hotkeys`: a registry plus the `?` shortcut sheet.
  - `virtual`: a windowed list and rows.
  - `dnd`: pointer and keyboard drag for sortable lists, kanban, tree and panel grid, with announcements.
  - `chart`: scales, ticks, time axis, paths, hit testing.
- **Icons:** one module per glyph, `DS.icons.<name>`, `data-ds-icon="<name>"`. The set grows from 109 to about 250
  (files, devices, charts, AI, editor, status, arrows, brands are out).

## Component catalogue

Origin:

## React adapter

`dist/react/` is an optional ES module with types. `react` (18 or later) is a peer that the project brings.
- Components are typed functions that render the documented markup with classes and `data-ds-*`. Props come from
  `meta.json`: `variant`, `size`, `tone` and the component's own props. Examples: `<Button variant="tonal" size="sm">`,
  `<Dialog open onClose>`, `<DataGrid columns rows onSort>`.
- Stateful widgets wrap the vanilla controller through a ref and an effect with cleanup. The cleanup is idempotent,
  so StrictMode's double effects are safe; a test runs under StrictMode.
- `<DSProvider>` calls `DS.init(root)` with the observer **on**. Plain markup inside React (a `data-ds-tooltip` on a
  `<span>`) still works that way, and adapter components mark their roots `data-ds-managed`, which the observer skips.
- The system writes some attributes to elements: ripple spans, `.ds-pressed`, `data-state`, `inert`, `popover`.
  - Each of these is written only on nodes React does not reconcile: a ripple layer the controller appends, or an
    element whose attribute React never sets.
  - The adapter's tests check that React re-renders keep them.
- Tested with React from a pinned dev-only copy under `test/react/` (a vendored UMD build, not an npm dependency), in
  the Playwright harness.
- Written without JSX (`createElement`), so it ships without a build step. Types are generated from `meta.json`.
- Tier 1 covers the components with JS plus Button, Field, Card, Badge, Status, Alert, Table and Tabs. The rest are
  plain markup and work through `className`.

## Phases and how the work runs in parallel

Phase 0 sets the foundations that every later phase relies on, and runs mostly in the main thread. From phase 1 on,
every component group is independent: its own folders, generated registries and no shared hand-edited file. So up to
about eight agents build in parallel, each in its own worktree branched from `next`. Each group is reviewed by an
independent agent before it merges back.

How the parallel groups stay apart:
- A group works only inside its folders, and hand-edits no shared file. Everything shared is generated
  ([Architecture](#architecture)).
- A group branch does not commit `dist/`, `package.json` or `CHANGELOG.md`. It writes its changelog lines into
  `<name>.md` (`## Changes`).
- One integrator, the main thread, merges each group into `next`, rebuilds `dist/`, assembles the changelog draft and
  runs the full checks.
- The allowlists of `css.test.js` (motion exceptions, `!important`, physical properties) move into `meta.json`, so
  each exception sits with its component and carries its reason.
- Screenshot baselines are written only from the CI container, as in 2.x. Groups test with `DS_SHOTS=local`, and the
  integrator triggers the CI update once per merge wave.

Every phase ends with `npm run check` and the browser tests green on `next`, and one commit series per group. Tier 2
and tier 3 items fill phases 2 and 3 when their group is ahead. Whatever is left is listed in a 3.1 plan.

### Carried-over infrastructure (checklist for phase 0)

- **Version:** the version banner on every output file, including the minified and single files; `DS.version`; the
  test that keeps them in step.
- **Copies:** `vendor.sh` and `vendor.ps1` handle the bigger `dist/`. `SHA256SUMS` stays one file. The many small
  files are acceptable, but they are measured against what `verify.sh` takes in CI.
- **Pages:** `site.sh` and the Pages workflow; a preview build of `next`.
- **Tokens:** `tokens.json` stays in its 2.x shape for one major, next to `tokens.dtcg.json`.
- **Motion Lab:** the coverage test of `lab.spec.js` and `LAB_EXEMPT` cover the new namespaces: every behaviour
  module and every core helper that moves something.
- **Removed names:** the guard in `repo.test.js` exempts `docs/migration.md` and the fixtures of `migrate.mjs`, since
  both must name the removed names.
- **Docs tests:** the tests that count docs files and names read the generated `docs/components/` tree.

This is many hours of agent work over several sessions, with a large token budget, mostly in phase 2.

## Risks

| Risk | Mitigation |
|---|---|
| The scale (about 170 items) dilutes quality | tiers; every item passes the same tests as 2.x; independent review per group; tier 3 waits rather than ships thin |
| A rewrite loses fixes that 2.x learned the hard way (WebKit row links, keyboard insets, flip timing, the overlay edge cases) | port before rewriting: the 2.x browser specs move along with each component and must pass unchanged in intent |
| Partial bundles behave differently from the full build | the layer statement in every bundle; a test renders the fixtures with the full and the partial bundle and compares them |
| Dynamic class names escape the scan | the tool fails on partial literals; safelist; `--check` in CI and in the nightly |
| `main` reaches projects by accident | 3.0 lives on `next` until the owner's merge decision ([Release](#release-and-protecting-the-projects)) |
| Size grows with the catalogue | minified builds, per-component budgets, bundles; icons and behaviours per file |
