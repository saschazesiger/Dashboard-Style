# Dashboard-Style 3.0: component conventions

This is the contract for every agent that ports or builds a component in phases 1 and 2. `plans/3.0.md` is the plan;
AGENTS.md holds the rules. Where this file is more specific, it wins.

## 1. One folder per component

Everything a component owns lives in `src/components/<n>/`. No other file is hand-edited for it, except those listed
in section 9. The build finds every file below by its name; any other file in the folder stops the build.

| File | Required | What |
|---|---|---|
| `<n>.css` | yes | One `@layer ds.components.<n> { … }` block, its own sublayer, opened by the layer statement every `src/` stylesheet starts with. The header comment describes the markup, variants, options, hooks, behaviour and "Progressive:" features, as in 2.x. Flat CSS: no nesting. The cascade between components (see below the table). |
| `meta.json` | yes | Validated against `scripts/meta-schema.json`, which describes every field, then checked against the folder and the CSS (the build fails on a difference). Required, in this order: `name`, `group`, `order` (cascade order, steps of 10), `docsOrder`, `need` (the one line of the need table; the demo repeats it, tested), `tier`, `status`, `classes`, `attributes`, `requires`, `context`, `hooks`, `keyframes`, `js`, `progressive`, `ripple`. Optional, in the schema's order: `keyframeDocs`, `module`, `rippleHosts`, `stateClasses`, `roles`, `labExempt`, `exceptions`, `motionExceptions`. `attributes` lists what the stylesheet's selectors name; a `data-ds-*` attribute only the module reads stays out (the build adds it to `manifest.json`, so a bundle finds the behaviour by it). `hooks` is an object: the owner describes each of its hooks (`"--ds-<n>-x": { "default": "…", "description": "…" }`, one row of the theming table; adjacent equal rows merge), a component that only reads another's hook names it (`{ "owner": "<other>" }`). |
| `<n>.md` | yes | The docs section in the style of `docs/components.md`:<br>- `##` title, one sentence of what it is for<br>- markup (copy-ready)<br>- options table (variant, size, tone, density, shape, where they apply)<br>- behaviour the page adds, or the `data-ds-*` API<br>- the JS API (controller, events): every export of `<n>.js` in a code span (tested)<br>- accessibility (keyboard, roles, names)<br>- forced colours<br>- hooks table<br>- motion, when it moves<br>Every class, hook and attribute appears here. |
| `<n>.demo.js` | yes | The styleguide demo (section 7). |
| `<n>.js` | when it has behaviour | An ES module, registered through `define()` of `core.js` (section 5). `meta.json` then has `"module": true` and lists `<n>` in `js`. The name is a JS identifier: `[a-z][a-z0-9]*`, no hyphen (it becomes `DS.<n>`). |
| `<n>.d.ts` | with `<n>.js` | Its types, with the module's parameter names (tested). Core types import from `'../../types/js/<core>.js'`. |
| `<n>.requires.json` | rarely | With `<n>.js`: `{ "requires": [], "exportRequires": { "<export>": ["<component>"] } }` when an export writes another component's markup (as `src/js/<module>.requires.json`, which may add `"attributes": ["data-ds-<x>"]`: attributes that need that core module on any component, so none credits them to the component that quotes them). |
| `<n>.test.js` | when it has JS or non-trivial CSS rules | Node unit tests (`node --test`); `npm test` runs `src/components/*/*.test.js`. Import the module as `./<n>.js`, helpers as `../../../test/helpers.js`. |
| `<n>.spec.js` | yes | Playwright: behaviour, keyboard, ARIA names, forced colours, and the motion timeline if it moves. It runs in the chromium, firefox and webkit projects, and in `fallback` when it imports `test` from `'../../../test/browser/base-test.js'` (helpers: `'../../../test/browser/helpers/motion.js'`). Its page is the generated fixture `/test/browser/fixtures/component.html?c=<n>` (the demo's `render()` and `wire()` alone through `styleguide/sg-core.js`, with the helpers of its styleguide page and `shell.css`, `dist/` loaded, `DS.init(document)` and `DS.ripple.attach(document)`, then `data-fixture-ready`, so `ready(page)` works; `&demo=<demo name>` renders one demo, `&min=1` loads `ds.min.*`), or its own `<n>.fixture.html` in the folder (served at `/src/components/<n>/<n>.fixture.html`). Screenshots and timelines go to `test/browser/__screenshots__/<project>/components/<n>/<n>.spec.js/` (`__screenshots-local__/` with `DS_SHOTS=local`). |
| `<n>.fixture.html` | rarely | A fixture page of its own, when the generated one is not enough. |
| `<n>.lab.js` | when it moves | Its Motion Lab entries (section 8). |
| `<n>.keyframes.css` | rarely | New `@keyframes`, prefixed `ds-`: the layer statement, then one `@layer ds.motion { … }` block of `@keyframes` only. Each name is listed in `meta.json` `keyframes` and documented in `keyframeDocs` (`{ "movement": "…", "use": "…" }`); the build appends them to `motion.css` in `ds.motion`, in component order, and checks every name once. A keyframe that names both ends needs `motionExceptions.keyframeShape`. Reuse existing keyframes first. |

**The cascade between components.** `src/index.css`, `ds.css`, every file of `dist/css/` and every bundle declare
`ds.components.global` (`src/core/global.css`) and then one sublayer per component in `meta.json` `order`. A later
sublayer wins over an earlier one whatever the specificity, so single files linked in any order, a partial bundle and
several bundles on one page cascade exactly as `ds.css` does. The build fails:
- a rule (or an at-rule statement) outside the file's own `@layer ds.components.<n>` block (`@property` and
  `@font-face` stay at the top level);
- a selector that names another component's class without that component in `context` (or `requires`), or that names
  it outside `:not()` and `:has()` while that component comes later in `order`. A class inside `:not()` or `:has()`
  only narrows the match, so it sets no order;
- a `context` entry whose classes the stylesheet does not name.

So a rule that two components meet in sits in the later of the two. Usually the component that gives the context
comes later and holds it: a card after what it places (`.ds-card > .ds-facts`), the page after the card
(`.ds-grid-2 > .ds-card`) and the loading bar (`.ds-page .ds-loadbar`), a table after the badge
(`.ds-table__row--selected .ds-badge`), the shell after the toast and the page. Where the contained component already
comes later, its own file holds it (`.ds-card .ds-table-wrap` in `table.css`, `.ds-table input[type=checkbox]` in
`form.css`). A rule of the earlier file that must leave a later component's element alone does so by selector, at no
weight (`.ds-form:where(:not(.ds-dialog__box))`, `.ds-grip:where(:not(:disabled, …))`), never by specificity. A
component's state classes that its module writes on other components' elements (the ripple's `.ds-pressed`, and
`.ds-ripples` on the root: `meta.json` `stateClasses`) are named freely and set no order. Reorder `order` when a
dependency is one-way; move the rule when two components would need each other first.

Generated from the folders, so never edit them by hand (`npm run build` writes them, `npm run check` compares them):
- `src/index.css`
- `docs/components.md`
- `styleguide/demos.js`
- `styleguide/lab-components.js` (the Motion Lab entries of every `<n>.lab.js`)
- `styleguide/registry.js` (every `meta.json`, the tokens, the need table)
- `styleguide/theme-generator.js` (`scripts/tools/{color,theme-rules,theme}.mjs` as a classic script)
- `dist/**`, with `dist/manifest.json` and the modules of `dist/js/`
- the generated blocks between `generated:` markers: the hooks table of `docs/theming.md`, the component keyframes
  table of `docs/motion.md`, the module table of `docs/install.md`, the module imports and namespaces of
  `src/types/ds.d.ts`, the ripple host list (`RIPPLE_HOSTS` in `src/js/ripple.js`) and the hooks of
  `themes/example.css`
- the component count of the README badge

## 2. Naming

| Concern | Form |
|---|---|
| Block, part | `.ds-<n>`, `.ds-<n>__<part>` |
| Variant (look) | `.ds-<n>--<variant>`. Shared variant names: `filled`, `tonal`, `outlined`, `text`, `ghost`, `elevated`, `quiet`, `plain`, `inset`. |
| Size | `.ds-xs`, `.ds-sm`, `.ds-md`, `.ds-lg`, `.ds-xl` on the element or any ancestor. 2.x `--sm` modifiers stay as aliases until 3.0 ships, then go into `deprecations.json` as removed, mapped to `.ds-sm`. |
| Tone | `.ds-tone-neutral`, `-primary`, `-info`, `-success`, `-warning`, `-error` |
| Density | `.ds-density-comfortable` (0), `-compact` (-1), `-dense` (-2), `-tight` (-3) on any container |
| Shape | `.ds-shape-square` (0), `-soft` (0.5), `-default` (1), `-round` (1.5) on any container or the theme |
| State | native attributes and ARIA first (`disabled`, `aria-expanded`, `aria-selected`, `aria-current`, `aria-busy`, `aria-invalid`), then `data-state` written by the system |
| Behaviour | `data-ds-<behaviour>`; options as `data-ds-<behaviour>-<option>`, or JSON in `data-ds-config` |
| Hooks | `--ds-<n>-<property>`, always read with a fallback |
| Events | `ds:<event>`, bubbling, through `emit()` of core |

Renaming a 2.x name is allowed where it buys consistency. Every rename gets a `src/deprecations.json` entry with
`removed: "3.0.0"` and `replacement`, so `tools/migrate.mjs` can map it. Keep a 2.x name as an alias only when the
plan says so.

## 3. Options: computed where they are used

The option classes (`src/core/options.css`, phase 1 prep) set **only** numeric custom properties, which inherit:
`--ds-size-step` (-2…2, default 0), `--ds-density` (0…-3, default 0) and `--ds-shape` (0…1.5, default 1). Tone classes
set `--ds-tone`, `--ds-on-tone`, `--ds-tone-container` and `--ds-on-tone-container` from the roles.

A component computes from them in its own rule, never on `.ds-theme`:

```css
.ds-btn {
  --_h: calc(var(--ds-btn-height, 40px) + var(--ds-size-step, 0) * 8px + var(--ds-density, 0) * 4px);
  block-size: max(var(--ds-target-min, 0px), var(--_h));
  border-radius: min(calc(var(--ds-btn-radius, var(--ds-radius-action)) * var(--ds-shape, 1)), calc(var(--_h) / 2));
}
```

- **Private computed properties** are named `--_<x>`. They exist only inside the rule that uses them, and they are
  never documented or themed.
- **Steps:**
  - Controls (button, field, chip, select, segmented, tabs): 8px per size step, 4px per density step.
  - Rows (list, table, menu item): 8px per size step, 4px per density step.
  - Padding of blocks and rows scales with density: `calc(var(--ds-<n>-padding, 16px) + var(--ds-density, 0) * 2px)`.
    A control's side padding is room for its label: it steps 4px per size and ignores density (the button).
  - An icon-only control (icon button) is a target with no label: it steps with size only, never with density.
  - Type changes with size only, through the size classes. They also set `--ds-size-font` (`xs`: caption; `sm`: chip;
    `md`: label; `lg`/`xl`: subtitle). A control reads `font: var(--ds-<n>-font, var(--ds-size-font, var(--ds-font-label)))`.
  - The base of a control is its md, comfortable value: the button is 40px, so `.ds-sm` (32px) and the compact
    density (32px) keep their 2.x heights.
- **Touch.** `.ds-touch` sets `--ds-target-min: var(--ds-touch-target)`. So touch wins over size and density, and the
  spec of every control proves it.
- **Shape.** Every radius is multiplied by `--ds-shape`. Actions take `min(min(radius, half) * shape, half)`: the pill
  at the default, rounded corners at `soft`, square at 0 (D11); and the press morph scales with it:
  `min(--ds-radius-action-pressed * shape, the rest radius)`.
- **Tones** apply where meaning is shown: badge, status, tag, alert, banner, chip, empty state, spinner, progress, meter,
  chart columns and legend keys, key-value icons, tile delta, prose callout, timeline, button.
  - On a button, only a filled `--ds-tone-error` is allowed, and only in a confirm dialog or a type-to-confirm (D10).
    The docs say so, and the button demo shows it in that context only.
  - Status is never shown by colour alone: a tone always comes with an icon or a word.
- **Type scale** (`--ds-type-scale`, default 1) and the font are theme-level: every `--ds-font-*` role in `tokens.css`
  multiplies its size and line height by it, resolves on `.ds-theme` and does not nest (docs/options.md says so).
  `--ds-font-input` never goes under 16/24. A component reads the roles and never sets the scale.
- **Layer.** `options.css` sits in `ds.utilities`, so a page's option class beats a component's own value of the same
  property on one element. The defaults are themeable values in `tokens.css` ("Options"), never read by a role.

## 4. Browser floor (D9): Safari 17.5, Chrome/Edge 123, Firefox 130

While porting, remove fallbacks for features now at the floor, and keep the progressive ones (plans/3.0.md, "Browser
floor").

At the floor, used directly:
- `linear()`, `@starting-style`, `transition-behavior: allow-discrete`
- `light-dark()` (colours only), `details[name]`, `popover` (always `manual`), `text-wrap: balance`, `:user-invalid`
- subgrid, `:has()`, container size queries, `color-mix()`, `oklch()`, `@property`

Progressive only, each named under "Progressive:" with its fallback:
- relative colour syntax, anchor positioning, View Transitions, scroll-driven animations
- `interpolate-size`, `::details-content`, `field-sizing`, `text-wrap: pretty`, style queries, `@scope`, `closedby`
- invoker commands, `appearance: base-select`, `moveBefore()`, Navigation API, iterator helpers, `sibling-index()`

The `fallback` Playwright project strips the right-hand column.

## 5. Behaviour modules

Each component with behaviour has `src/components/<n>/<n>.js`, an ES module. There is no list to edit: the build
discovers the file (`meta.json` says `"module": true` and lists `<n>` in `js`), orders it after the core modules and
after every component module it imports (a cycle or an unknown import stops the build), bundles it into `ds.js` and
`ds.min.js` as `DS.<n>`, and lists it in `manifest.json` `js`, `src/types/ds.d.ts` and the module table of
`docs/install.md`. In `dist/` every module sits flat in one folder: `dist/js/<n>.js`, with `dist/js/<n>.d.ts`, its
imports rewritten to `./<module>.js`. So `<n>` is a JS identifier, not the name of a core module, and folders with
a hyphen in their name take no module. The module does three things:

1. Imports what it needs from the core modules (`core`, `motion`, `dom`, `overlay` and the phase 1 helpers `a11y`,
   `position`, `format`, `store`, `hotkeys`, `virtual`, `dnd`), one named-import line each, with these paths:
   `import { define, emit } from '../../js/core.js';`; another component's module as
   `import { open } from '../menu/menu.js';`. Node and browsers resolve these paths as they stand, so `<n>.test.js`
   imports `./<n>.js` directly.
2. Registers: `define('<n>', { attribute: 'data-ds-<n>', init(el, ctx) { …; return controller; } })`.
   - Delegated behaviours use `global(root)`, and the cleanup they return is idempotent.
   - The `ctx.signal` (an `AbortSignal`) removes every listener on destroy.
3. Exports the imperative API as `export function`, such as `export function open(el, options)` or
   `export function create(el, options)`. It returns the same controller the attribute path makes.

The controller has one shape:
- `get()` and `set(value)` for its state or value
- `on(type, fn)`, which returns an unsubscribe
- `destroy()`
- events through `ctx.emit(el, '<type>', detail)`, which dispatches `ds:<type>`

Further rules:
- **Controlled versus uncontrolled.** `data-ds-value` or the markup's state is the initial state, and `set()` drives
  it from the page.
- **Rendering.** Never `innerHTML` on page content. Render the component's own parts with `DS.dom.morphHtml` or DOM
  APIs, and key list rows with `data-ds-key`.
- **Timing** comes from `motionDuration()`, never ms literals. New fallbacks go into `MOTION_FALLBACKS`.
- **Strings** go through `ctx.t('<key>')`. Add new keys to `core.js` `DEFAULT_STRINGS` (section 9). A UI string
  written anywhere else in the module fails `test/repo.test.js` ("every built-in UI string"), also a template literal.
- **Language.** ES2022. Only `export const` and `export function`. Newer APIs only behind feature detection, named
  under "Progressive:" in the module header.
- **Types** go in `src/components/<n>/<n>.d.ts`, hand-written, with the same parameter names as the module (tested);
  core types import from `'../../types/js/<core>.js'`, another component's from `'../<other>/<other>.js'`.
- **Docs.** Every export is named in a code span of `<n>.md` (tested, as `docs/motion.md` is for the core).
- **Motion Lab.** Every exported function appears in the `shows` of a `<n>.lab.js` entry, or in `meta.json`
  `labExempt` with its reason (`"DS.<n>.create": "events only, no motion"`); the coverage test of `lab.spec.js` fails
  otherwise.
- **Runtime properties.** A `--ds-<n>-x` the module writes (quoted in `<n>.js`) counts as a runtime property by
  itself; it is no hook and needs no row in the hooks table.
- **Overlays** open and close only through `DS.overlay` (`open`, `close`, the stack, Escape order, focus return, the
  scroll lock), and stay inside `.ds-theme`. Popovers are `popover="manual"`; light dismiss goes through
  `DS.overlay`.

## 6. Tokens and colour roles

- **No literals** for colour, radius, shadow, font, duration, curve, opacity or z-index. Read roles and scales, and
  give hooks fallbacks.
- **A new hook** is just read with a fallback and described in `meta.json` `hooks`
  (`"--ds-<n>-x": { "default": "…", "description": "…" }`). The build writes the theming table and the hooks of
  `themes/example.css`. A hook with no value of its own (`--ds-btn-height-exact`) has the default `"unset"`: no default
  in `tokens.json`, `(unset)` in `themes/example.css`.
- **A new colour role** is rare. Prefer existing roles and `color-mix()` of them. If one is needed, declare it in
  `meta.json` `roles`:
  `{ "--ds-x": { "light": "…", "dark": "…", "contrast": "…", "pair": ["--ds-x", "--ds-surface", "text|control|icon"] } }`.
  The integrator moves it into `tokens.css`, the themes, `theme-rules.mjs` and the generator; do not edit those files
  yourself.
- **Motion tokens only.** Themes never set motion tokens or motion hooks.

## 7. Demos (`<n>.demo.js`)

A classic script, so the styleguide works from `file://`. It imports and exports nothing. The build wraps each file in
a function of its own (its top-level names stay private) and concatenates them into `styleguide/demos.js`, which the
pages load after `styleguide/sg-core.js`. Each file calls `SG.demo` once, with its folder's name (the build fails
otherwise):

```js
SG.demo('<n>', {
  title: 'Date picker',                 // page and drawer title
  group: 'forms',                       // same as meta.json
  need: 'Pick one date or a range; type it or choose it',
  lead: '…',                            // optional: a longer intro under the title
  options: { variants: ['outlined', 'filled'], sizes: true, density: true, tones: false, shape: true },
  render: function (h) { return '…markup…'; },
  wire: function (root, h) { /* optional; may return a cleanup function */ }
});
```

**Options.** They say what the options panel offers.
- `variants`: a list of names; `render` reads `h.variant` (`null` means: show every variant).
- `tones`: `true` (all six) or a list; `render` may read `h.tone`.
- `sizes`, `density`, `shape`: `true` or a list of their values. The panel offers every value when the key is
  absent, and nothing when it is `false`.

**Applied around the demo.** The panel sets these on the stage, which is a `.ds-theme` of its own:
- `.ds-<size>`, `.ds-density-<level>`, `.ds-shape-<level>`, `.ds-tone-<tone>` and `.ds-touch` (a default adds no
  class, so a theme's own density or shape shows)
- `data-ds-scheme` (light, dark; auto removes it)
- the width, as the stage's `inline-size` (360px to full)
- the preset and the contrast load `dist/themes/presets/<name>[-contrast].css` for the whole page

`render` runs again only when the variant or the tone changes; everything else changes classes and attributes only.
So a component reacts to them through CSS, as it will in a project.

**Helpers `h`** (the same object for `render` and `wire`):

| Helper | What |
|---|---|
| `icon(name, size = 20, cls)` | a glyph of `DS.icons` as markup |
| `esc(text)` | text escaped for markup |
| `uid(prefix)` | an id unique on the page (`sg-<prefix>-<n>`): use it for `for`, `aria-controls` and `aria-labelledby`, never a fixed id |
| `card(title, body, extra)` | a `.ds-card` with its title (`extra`: attributes as text) |
| `section(title, body, lead)` | a titled block of the demo (Variants, States, Sizes, Narrow) |
| `toast(text, kind)` | a snackbar through `DS.overlay.toast` (`success`, `info`, `error`) |
| `$(selector, root)`, `$$(…)` | `querySelector`, and `querySelectorAll` as an array |
| `slow(ms)` | a demo timer's delay at the styleguide's speed (`?speed=0.1` makes it ten times longer) |
| `variant`, `tone`, `options` | the panel's current choices |

**`wire(root, h)`** holds only what a project would write itself: page-side listeners, fake data, the toast after an
action. Behaviour comes from the system (`data-ds-*`, `DS.init`); the page has already called `DS.init(document)`
and `DS.ripple.attach(document)`.
- `root` is a fresh element per render. Listeners on it go with it.
- Listeners on `document` or `window` need the cleanup function that `wire` returns.
- Query inside `root` only (`h.$('…', root)`).

**API of `sg-core.js`.** Its header documents it. The harness fixtures use it too:
- `SG.mount(name, stage, choice)` renders and wires a demo with a choice applied around it, and returns
  `{ root, spec, update(choice), destroy() }`.
- `SG.get`, `SG.list`, `SG.choices`, `SG.applyOptions`, `SG.optionClasses`, `SG.helpers`, `SG.OPTIONS`.

**Pages and registry.**
- `styleguide/index.html` builds a page per registered demo (`#/components/<n>`).
- The drawer comes from the registered demos, grouped by `meta.json` `group`.
- `styleguide/registry.js` is generated from the `meta.json` files: name, group, `need`, `tier`, `status`, classes,
  attributes, hooks, and the tokens of `tokens.css`. It feeds the search and the "Which component for which need"
  page.
- A component without a demo (none today) shows a page that links its docs.
- `styleguide/demos.js`, `styleguide/registry.js` and `styleguide/theme-generator.js` are generated: never edit them.
- The theme page runs `theme-generator.js`, a classic script, so it works from `file://` in every engine (tested).

**Limits.**
- The width option narrows what queries the `ds-content` container (the stage is that container). Media queries do
  not follow it: `.ds-grid-2` and the drawer react to the window only. A component that should narrow with its
  container uses a container query.
- The preset, the contrast and the theme file apply to the whole page, since a theme file selects `.ds-theme` and
  cannot be scoped to the stage. The colour scheme is one choice for the page and the stage.

**Content.** Generic, as in 2.x: devices, tickets, "Product", Ada Lovelace. Never a real project, organisation,
place or brand (`test/repo.test.js`).

**Coverage.** Show every variant and the states (disabled, busy, error, empty), keyboard use and a narrow width. The
options panel applies size, density, shape, tone and theme around the demo, so the demo need not repeat them.
Every registered demo must render without console errors: `test/browser/styleguide-v3.spec.js` opens each one.

### The 2.x styleguide is retired

Phase 1 moved every 2.x section of `styleguide/styleguide.js` (`legacy.html`) into a `<n>.demo.js`, and its last
step (3.0.0-alpha.4) deleted both. The foundations, the theme choices of its theme select (the shipped theme files
and two snippets, now "Theme file" in the options) and its frame live on in the 3.0 shell; an old address
(`index.html#buttons`) opens the page that took the section over. The Motion Lab keeps the 2.x frame in
`styleguide/motion-lab.js`. The specs that opened `legacy.html` open the component pages, the fixtures or the
Motion Lab. `src/components/button/button.demo.js` stays the worked example of the options: it renders no size
class (the panel's classes reach it), reads `h.variant` and `h.tone`, and `styleguide-v3.spec.js` measures every
option on it. A new component gets its demo with its folder; there is nothing left to port.

## 8. Motion

- **Rules.** Every AGENTS.md motion rule holds: tokens only, the spring for movement that floats, `--ds-ease-out` for
  sizes, exits at 0.3-0.8 of their entrance, interrupted motion continues, hover never moves, and nothing scales on
  press except the switch handle.
- **Named exceptions.**
  - The D14 ones: chart path morph, tour spotlight glide, carousel slide.
  - The bottom sheet's drag.
  - Anything else needs a reason in `meta.json` `motionExceptions`, which the tests read, and a line in the report:
    `transition.<property>` (`rotate`, `width`, `height` and the other named properties of the animate list: selector
    → reason), `exitUnpaired` (a movement exit without `ds-fade-out`), `keyframeShape` (a keyframe of the folder that
    names both ends or many stops) and `press` (a pressed selector that scales; only the switch handle). Every key
    names one of the component's own classes (a keyframe: one of its own); the build checks it.
- **Motion Lab.** Every moving thing gets an entry in `<n>.lab.js`, a classic script the build concatenates into
  `styleguide/lab-components.js` (loaded by `motion.html` after `lab.js`). It calls `SG_LAB.add(entry)` with the entry
  shape the head of `styleguide/lab.js` documents:
  ```js
  SG_LAB.add({
    id: '<n>-open',                // unique
    group: 'overlays',             // a section: foundations, utilities, keyframes, data, controls, navigation, overlays, feedback, views
    title: 'Picker opens',
    shows: ['ds-keyframe', '.ds-class', 'DS.<n>.open', '--ds-token'],   // what it plays
    html: '<div class="…">…</div>',  // the stage markup
    play: function (stage, sg) { /* … */ return DS.motion.settled(el); },   // a Promise that resolves once settled
    toggle: function (stage, on, sg) { /* optional, when reversible: towards `on` from wherever it is */ },
    // optional too: note, height, after, controls, wide, playLabel, setup, state, reset, subject
  });
  ```
  A bad entry or a taken `id` throws. The coverage test of `lab.spec.js` sees these entries and fails for a keyframe,
  motion class or function of `DS.<n>` that no `shows` names and no `meta.json` `labExempt` excuses.

## 9. Shared files: what you may touch

- **Do not edit** (the integrator does it from your report):
  - `src/core/tokens.css`, `themes/*`, `scripts/tools/theme-rules.mjs`
  - `src/core/motion.css`, `scripts/build.mjs`
  - `package.json`, `CHANGELOG.md`, `README.md`, `AGENTS.md`
  - `dist/`, and any other component's folder
- **May append to:**
  - `src/js/core.js` `DEFAULT_STRINGS`, a key-value line per string
  - `src/js/icons.js`, a glyph only if truly missing, in the same style
  - `src/deprecations.json`, entries
- **Allowlists** that concern one component live in its `meta.json`, each key with its reason: `exceptions.important`
  and `exceptions.physical` (`"<selector>: <property>"`), `exceptions.hover` (a selector), `exceptions.focus`,
  `exceptions.ripple` and `exceptions.scroller` (a class), and `motionExceptions` (section 8). The build checks that a
  key names one of the component's own classes; `test/css.test.js` reads them and fails on a stale `important`,
  `physical`, `ripple` or `motionExceptions.transition` entry. Only what no component owns stays in the test (the core
  stylesheets, the `input` halo).
- **Ripple hosts.** A new host is `meta.json` `"rippleHosts": ["<selector>"]` with `"ripple": true`. The build writes
  the `RIPPLE_HOSTS` list of `src/js/ripple.js` from them. The host's pressed `:where(.ds-ripples) <selector>…` rule
  (the flat layer stays at its hover value) goes in the component's own stylesheet, after its press rule, and the test
  looks for it there too. The rules of the 2.x hosts stay hand-edited in `ripple.css`: each differs (the layer's
  values, the chip's and the table row's parts, the media queries), so generating them would make the CSS worse, and
  only the list was shared.
  - **Its sublayer is the last one** (decided with the sublayers, 3.0.0-alpha.4; its `order` is 9990, and the build
    fails a component ordered after it). The ripple's own box
    (`.ds-press-ripple`: absolute, behind the content, sized by the script) must win over any rule of a host that
    reaches its children (`.ds-list__item > :not(…)` once had to leave it out by name); in the last sublayer it
    does, whatever a host adds later. Its rules for the 2.x hosts leave the blocked states out by selector, so they
    hold in any later layer as well (`ripple.spec.js` plays the file once more in `ds.utilities`), and the tab's and
    the table row's ripple boxes stay next to the box they override. Moving those rules into the hosts would have
    put the ripple first and every host's child rules above its box. A host names `.ds-pressed` and `.ds-ripples`
    (`stateClasses`) without listing ripple in `context`; the build keeps every host before ripple.
- **Generated files stay out of a group branch, like `dist/`.** Parallel branches would collide on them, and the
  integrator rebuilds them after each merge. `npm run build`, then `npm test`; before committing restore them:
  `git checkout -- dist $(node scripts/build.mjs --generated)`.
- **CHANGELOG.** Write your lines at the end of your `<n>.md` under `<!-- changelog -->`, which the integrator moves.

## 10. Definition of done (per component)

1. CSS, `meta.json`, md, demo, spec, plus JS, unit test and lab entry when they apply, all to these conventions.
2. `npm run build && npm test` passes in your worktree. Then `git checkout -- dist $(node scripts/build.mjs --generated)`
   before committing (section 9).
3. Browser: your own spec, plus any 2.x spec of this component, pass in chromium, firefox and webkit, and the
   `fallback` project where the spec imports `base-test.js`.
   - Command: `DS_SHOTS=local DS_TEST_PORT=<your port> npx playwright test <specs> --project=chromium --project=firefox --project=webkit`.
   - Never run the whole suite; the machine is shared.
4. Forced colours checked (spec). Keyboard complete (spec). Names and roles checked (spec).
5. A port keeps every 2.x behaviour. Its 2.x browser specs pass unchanged in intent; an assertion may change only
   where the 3.0 API renamed something, and the report names each such change.
6. **Process on the shared machine.** It keeps these rules out of false failures and other agents' runs:
   - `export TMPDIR=/var/tmp/ds3/tmp` (mkdir it): `/tmp` is a nearly full tmpfs, and a full one fails tests with ENOSPC
     or "Target crashed" that have nothing to do with the change.
   - Never `pkill -f` with a pattern: other chats' and agents' processes match it, and it has already killed runs and
     its own shell. Stop only PIDs you started; a leftover server is found by its cwd and start time.
   - Pass `--config test/browser/playwright.config.js` and a `DS_TEST_PORT` of your own; run the whole browser suite with
     at most `--workers=4`.
   - Compare a suspected flake with the base commit in a `git worktree` before calling it pre-existing.
7. The report, at most 200 words: branch, commits, components done, renames, roles requested, strings added,
   motion exceptions, and anything left open.

## 11. Reference port: button

`src/components/button/` is the worked example (commit "Button: the reference port to the options model"). What was
done, in order; do the same for your component:

1. **Read the 2.x file first** and list what it does: variants, hooks, states, the press and focus model, forced
   colours, the browser specs that cover it, and every other component that reads one of its hooks (here: alert,
   table, page head, card row, inline form and the drawer row read `--ds-btn-height` or the icon sizes to line up).
2. **Compute the options in the component's own rule**, into private properties: `--_h` (the hook as the md,
   comfortable base, plus `--ds-size-step * 8px` and `--ds-density * 4px`, or an `-exact` hook), `--_box`
   (`max(var(--ds-target-min, 0px), var(--_h))`), `--_half`, `--_radius` (the pill times `--ds-shape`, at most
   `--_half`), `--_pad`. Read every option with a fallback (`var(--ds-density, 0)`), so a page that links the
   component without `options.css` still works. Variants override the private values (`--icon` sets its own `--_box`),
   never the public hooks.
3. **Decide what each option does not touch**, and write it in the header and the md: the button's density changes
   height only (not side padding, not icon buttons); type follows size only.
4. **Keep the 2.x look where a theme relies on it.** Pick the base so the old values fall on the new steps (40px base:
   `sm` and compact density give 2.x's 32px), and prove it: the styleguide in `compact` was compared section by section
   against the 2.x tree (pixel-identical). An alias that cannot follow the model exactly keeps its 2.x geometry (`--sm`:
   fixed 32px, its own density 0 so the components that line up with it still compute 32px).
5. **Update the readers.** A component that lines up with yours computes the same formula
   (`max(var(--ds-target-min, 0px), calc(var(--ds-btn-height, 40px) + var(--ds-size-step, 0) * 8px + var(--ds-density, 0) * 4px))`),
   never a stale fallback. Move what `.ds-touch` did through hooks to `--ds-target-min` and drop those hooks from
   `utilities.css`.
6. **Rename to the shared names** (`--primary` → `--filled`), keep the 2.x name as a selector alias, add a
   `deprecations.json` entry (`removed: "3.0.0"`, `replacement`), mark it **deprecated** in the md, and migrate
   `example/` and `demo/` in the same commit (check-project runs on them).
7. **Tones**: read the tone only where the component shows meaning, and only from the class on the element itself
   when an inherited tone would mislead (`:is(.ds-btn--filled).ds-tone-error`); always with an icon or a word.
8. **Add the missing states the catalogue asks for** with the 2.x mechanics (the failed face mirrors the done face;
   `DS.motion.busy()` sets it), and the variants (`--elevated`, `--ghost`, `--block`), each with its hook (`-shadow`)
   described in `meta.json` `hooks`; the build writes the theming table and `themes/example.css`.
9. **Drop fallbacks the floor made unnecessary** and update the "Progressive:" note (the button had none left).
10. **Docs**: the md gets an options table (option, classes, where it applies, effect), the D10/D11 rules, keyboard,
    forced colours and the changelog lines; `meta.json` lists the new classes and hooks (the build checks them).
