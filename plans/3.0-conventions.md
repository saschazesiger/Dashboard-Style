# Dashboard-Style 3.0: component conventions

This is the contract for every agent that ports or builds a component in phases 1 and 2. `plans/3.0.md` is the plan;
AGENTS.md holds the rules. Where this file is more specific, it wins.

## 1. One folder per component

Everything a component owns lives in `src/components/<n>/`. No other file is hand-edited for it, except those listed
in section 9.

| File | Required | What |
|---|---|---|
| `<n>.css` | yes | One `@layer ds.components { … }` block, opened by the layer statement every `src/` stylesheet starts with. The header comment describes the markup, variants, options, hooks, behaviour and "Progressive:" features, as in 2.x. Flat CSS: no nesting. |
| `meta.json` | yes | The fields of the existing ones (`name`, `group`, `order`, `docsOrder`, `classes`, `attributes`, `requires`, `context`, `hooks`, `keyframes`, `js`, `progressive`, `ripple`), plus `need`, `tier`, `status` and `roles` (section 6). The build fails when it differs from the CSS. |
| `<n>.md` | yes | The docs section in the style of `docs/components.md`:<br>- `##` title, one sentence of what it is for<br>- markup (copy-ready)<br>- options table (variant, size, tone, density, shape, where they apply)<br>- behaviour the page adds, or the `data-ds-*` API<br>- the JS API (controller, events)<br>- accessibility (keyboard, roles, names)<br>- forced colours<br>- hooks table<br>- motion, when it moves<br>Every class, hook and attribute appears here. |
| `<n>.demo.js` | yes | The styleguide demo (section 7). |
| `<n>.js` | when it has behaviour | An ES module, registered through `define()` of `core.js` (section 5). |
| `<n>.test.js` | when it has JS or non-trivial CSS rules | Node unit tests (`node --test`). |
| `<n>.spec.js` | yes | Playwright: behaviour, keyboard, ARIA names, forced colours, and the motion timeline if it moves. Uses the fixture page the harness generates from the demo, or its own fixture in the folder. |
| `<n>.lab.js` | when it moves | Its Motion Lab entries (section 8). |
| `<n>.keyframes.css` | rarely | New `@keyframes`, prefixed `ds-`, each listed in `meta.json` `keyframes`. The build appends them to `motion.css` in `ds.motion`. Reuse existing keyframes first. |

Generated from the folders, so never edit them by hand:
- `src/index.css`
- `docs/components.md`
- `styleguide/demos.js`
- `dist/**`
- the hooks table of `docs/theming.md`
- the ripple host list
- the Motion Lab registry
- `dist/manifest.json`

## 2. Naming

| Concern | Form |
|---|---|
| Block, part | `.ds-<n>`, `.ds-<n>__<part>` |
| Variant (look) | `.ds-<n>--<variant>`. Shared variant names: `filled`, `tonal`, `outlined`, `text`, `ghost`, `elevated`, `quiet`, `plain`, `inset`. |
| Size | `.ds-xs`, `.ds-sm`, `.ds-md`, `.ds-lg`, `.ds-xl` on the element or any ancestor. 2.x `--sm` modifiers stay as aliases until 3.0 ships, then go into `deprecations.json` as removed, mapped to `.ds-sm`. |
| Tone | `.ds-tone-neutral`, `-primary`, `-info`, `-success`, `-warning`, `-error` |
| Density | `.ds-density-comfortable` (0), `-compact` (-1), `-dense` (-2), `-tight` (-3) on any container |
| Shape | `.ds-shape-square` (0), `-soft` (0.5), `-default` (1), `-round` (1.5) on any container or the theme |
| State | native attributes and ARIA first (`disabled`, `aria-expanded`, `aria-selected`, `aria-current`, `aria-busy`, `aria-invalid`), then `data-state` written by the system |
| Behaviour | `data-ds-<behaviour>`; options as `data-ds-<behaviour>-<option>`, or JSON in `data-ds-config` |
| Hooks | `--ds-<n>-<property>`, always read with a fallback |
| Events | `ds:<event>`, bubbling, through `emit()` of core |

Renaming a 2.x name is allowed where it buys consistency. Every rename gets a `src/deprecations.json` entry with
`removed: "3.0.0"` and `replacement`, so `tools/migrate.mjs` can map it. Keep a 2.x name as an alias only when the
plan says so.

## 3. Options: computed where they are used

The option classes (`src/core/options.css`, phase 1 prep) set **only** numeric custom properties, which inherit:
`--ds-size-step` (-2…2, default 0), `--ds-density` (0…-3, default 0) and `--ds-shape` (0…1.5, default 1). Tone classes
set `--ds-tone`, `--ds-on-tone`, `--ds-tone-container` and `--ds-on-tone-container` from the roles.

A component computes from them in its own rule, never on `.ds-theme`:

```css
.ds-btn {
  --_h: calc(var(--ds-btn-height, 40px) + var(--ds-size-step, 0) * 8px + var(--ds-density, 0) * 4px);
  block-size: max(var(--ds-target-min, 0px), var(--_h));
  border-radius: min(calc(var(--ds-btn-radius, var(--ds-radius-action)) * var(--ds-shape, 1)), calc(var(--_h) / 2));
}
```

- **Private computed properties** are named `--_<x>`. They exist only inside the rule that uses them, and they are
  never documented or themed.
- **Steps:**
  - Controls (button, field, chip, select, segmented, tabs): 8px per size step, 4px per density step.
  - Rows (list, table, menu item): 8px per size step, 4px per density step.
  - Padding scales with density: `calc(var(--ds-<n>-padding, 16px) + var(--ds-density, 0) * 2px)`.
  - Type changes with size only, through the size classes. They also set `--ds-size-font` (`xs`/`sm`: the chip or
    meta role; `md`: label; `lg`/`xl`: subtitle). A control reads `font: var(--ds-<n>-font, var(--ds-size-font, var(--ds-font-label)))`.
- **Touch.** `.ds-touch` sets `--ds-target-min: var(--ds-touch-target)`. So touch wins over size and density, and the
  spec of every control proves it.
- **Shape.** Every radius is multiplied by `--ds-shape`. Actions stay `min(radius, half the height)`. So a square theme
  gets square buttons (D11), and the press morph scales with it:
  `--ds-radius-action-pressed` is multiplied by `--ds-shape` too.
- **Tones** apply where meaning is shown: badge, status, alert, banner, chip, progress, meter, button.
  - On a button, only a filled `--ds-tone-error` is allowed, and only in a confirm dialog or a type-to-confirm (D10).
    The docs say so, and the button demo shows it in that context only.
  - Status is never shown by colour alone: a tone always comes with an icon or a word.
- **Type scale** (`--ds-type-scale`) and the font are theme-level. They are read on `.ds-theme` and do not nest; say
  so in the docs.

## 4. Browser floor (D9): Safari 17.5, Chrome/Edge 123, Firefox 130

While porting, remove fallbacks for features now at the floor, and keep the progressive ones (plans/3.0.md, "Browser
floor").

At the floor, used directly:
- `linear()`, `@starting-style`, `transition-behavior: allow-discrete`
- `light-dark()` (colours only), `details[name]`, `popover` (always `manual`), `text-wrap: balance`, `:user-invalid`
- subgrid, `:has()`, container size queries, `color-mix()`, `oklch()`, `@property`

Progressive only, each named under "Progressive:" with its fallback:
- relative colour syntax, anchor positioning, View Transitions, scroll-driven animations
- `interpolate-size`, `::details-content`, `field-sizing`, `text-wrap: pretty`, style queries, `@scope`, `closedby`
- invoker commands, `appearance: base-select`, `moveBefore()`, Navigation API, iterator helpers, `sibling-index()`

The `fallback` Playwright project strips the right-hand column.

## 5. Behaviour modules

Each component with behaviour has `src/components/<n>/<n>.js`, an ES module (the integration notes of wave 0 give the
exact import path and build registration; follow them). It does three things:

1. Imports what it needs from the core modules (`core`, `motion`, `dom`, `overlay` and the phase 1 helpers `a11y`,
   `position`, `format`, `store`, `hotkeys`, `virtual`, `dnd`), one named-import line each.
2. Registers: `define('<n>', { attribute: 'data-ds-<n>', init(el, ctx) { …; return controller; } })`.
   - Delegated behaviours use `global(root)`, and the cleanup they return is idempotent.
   - The `ctx.signal` (an `AbortSignal`) removes every listener on destroy.
3. Exports the imperative API as `export function`, such as `export function open(el, options)` or
   `export function create(el, options)`. It returns the same controller the attribute path makes.

The controller has one shape:
- `get()` and `set(value)` for its state or value
- `on(type, fn)`, which returns an unsubscribe
- `destroy()`
- events through `ctx.emit(el, '<type>', detail)`, which dispatches `ds:<type>`

Further rules:
- **Controlled versus uncontrolled.** `data-ds-value` or the markup's state is the initial state, and `set()` drives
  it from the page.
- **Rendering.** Never `innerHTML` on page content. Render the component's own parts with `DS.dom.morphHtml` or DOM
  APIs, and key list rows with `data-ds-key`.
- **Timing** comes from `motionDuration()`, never ms literals. New fallbacks go into `MOTION_FALLBACKS`.
- **Strings** go through `ctx.t('<key>')`. Add new keys to `core.js` `DEFAULT_STRINGS` (section 9).
- **Language.** ES2022. Only `export const` and `export function`. Newer APIs only behind feature detection, named
  under "Progressive:" in the module header.
- **Types** go in `src/types/js/<n>.d.ts`, generated or hand-written as wave 0 established, with the same parameter
  names as the module.
- **Overlays** open and close only through `DS.overlay` (`open`, `close`, the stack, Escape order, focus return, the
  scroll lock), and stay inside `.ds-theme`. Popovers are `popover="manual"`; light dismiss goes through
  `DS.overlay`.

## 6. Tokens and colour roles

- **No literals** for colour, radius, shadow, font, duration, curve, opacity or z-index. Read roles and scales, and
  give hooks fallbacks.
- **A new hook** is just read with a fallback and listed in `meta.json` `hooks`. The build writes the theming table.
- **A new colour role** is rare. Prefer existing roles and `color-mix()` of them. If one is needed, declare it in
  `meta.json` `roles`:
  `{ "--ds-x": { "light": "…", "dark": "…", "contrast": "…", "pair": ["--ds-x", "--ds-surface", "text|control|icon"] } }`.
  The integrator moves it into `tokens.css`, the themes, `theme-rules.mjs` and the generator; do not edit those files
  yourself.
- **Motion tokens only.** Themes never set motion tokens or motion hooks.

## 7. Demos (`<n>.demo.js`)

A classic script, so the styleguide works from `file://`. It imports and exports nothing. The build wraps each file in
a function of its own (its top-level names stay private) and concatenates them into `styleguide/demos.js`, which the
pages load after `styleguide/sg-core.js`. Each file calls `SG.demo` once, with its folder's name (the build fails
otherwise):

```js
SG.demo('<n>', {
  title: 'Date picker',                 // page and drawer title
  group: 'forms',                       // same as meta.json
  need: 'Pick one date or a range; type it or choose it',
  lead: '…',                            // optional: a longer intro under the title
  options: { variants: ['outlined', 'filled'], sizes: true, density: true, tones: false, shape: true },
  render: function (h) { return '…markup…'; },
  wire: function (root, h) { /* optional; may return a cleanup function */ }
});
```

**Options.** They say what the options panel offers.
- `variants`: a list of names; `render` reads `h.variant` (`null` means: show every variant).
- `tones`: `true` (all six) or a list; `render` may read `h.tone`.
- `sizes`, `density`, `shape`: `true` or a list of their values. The panel offers every value when the key is
  absent, and nothing when it is `false`.

**Applied around the demo.** The panel sets these on the stage, which is a `.ds-theme` of its own:
- `.ds-<size>`, `.ds-density-<level>`, `.ds-shape-<level>`, `.ds-tone-<tone>` and `.ds-touch` (a default adds no
  class, so a theme's own density or shape shows)
- `data-ds-scheme` (light, dark; auto removes it)
- the width, as the stage's `inline-size` (360px to full)
- the preset and the contrast load `dist/themes/presets/<name>[-contrast].css` for the whole page

`render` runs again only when the variant or the tone changes; everything else changes classes and attributes only.
So a component reacts to them through CSS, as it will in a project.

**Helpers `h`** (the same object for `render` and `wire`):

| Helper | What |
|---|---|
| `icon(name, size = 20, cls)` | a glyph of `DS.icons` as markup |
| `esc(text)` | text escaped for markup |
| `uid(prefix)` | an id unique on the page (`sg-<prefix>-<n>`): use it for `for`, `aria-controls` and `aria-labelledby`, never a fixed id |
| `card(title, body, extra)` | a `.ds-card` with its title (`extra`: attributes as text) |
| `section(title, body, lead)` | a titled block of the demo (Variants, States, Sizes, Narrow) |
| `toast(text, kind)` | a snackbar through `DS.overlay.toast` (`success`, `info`, `error`) |
| `$(selector, root)`, `$$(…)` | `querySelector`, and `querySelectorAll` as an array |
| `slow(ms)` | a demo timer's delay at the styleguide's speed (`?speed=0.1` makes it ten times longer) |
| `variant`, `tone`, `options` | the panel's current choices |

**`wire(root, h)`** holds only what a project would write itself: page-side listeners, fake data, the toast after an
action. Behaviour comes from the system (`data-ds-*`, `DS.init`); the page has already called `DS.init(document)`
and `DS.ripple.attach(document)`.
- `root` is a fresh element per render. Listeners on it go with it.
- Listeners on `document` or `window` need the cleanup function that `wire` returns.
- Query inside `root` only (`h.$('…', root)`).

**API of `sg-core.js`.** Its header documents it. The harness fixtures use it too:
- `SG.mount(name, stage, choice)` renders and wires a demo with a choice applied around it, and returns
  `{ root, spec, update(choice), destroy() }`.
- `SG.get`, `SG.list`, `SG.choices`, `SG.applyOptions`, `SG.optionClasses`, `SG.helpers`, `SG.OPTIONS`.

**Pages and registry.**
- `styleguide/index.html` builds a page per registered demo (`#/components/<n>`).
- The drawer comes from the registered demos, grouped by `meta.json` `group`.
- `styleguide/registry.js` is generated from the `meta.json` files: name, group, `need`, `tier`, `status`, classes,
  attributes, hooks, and the tokens of `tokens.css`. It feeds the search and the "Which component for which need"
  page.
- A component without a demo links to its 2.x section on `styleguide/legacy.html`.
- `styleguide/demos.js` and `styleguide/registry.js` are generated: never edit them.

**Limits.**
- From `file://`, only Firefox loads the theme generator (an ES module). Chromium and WebKit block the import, log one
  console error, and the theme page offers the shipped presets and says how to serve the folder. Over http it runs in
  all three engines.
- The width option narrows what queries the `ds-content` container (the stage is that container). Media queries do
  not follow it: `.ds-grid-2` and the drawer react to the window only. A component that should narrow with its
  container uses a container query.
- The preset and the contrast apply to the whole page, since a theme file selects `.ds-theme` and cannot be scoped to
  the stage. The colour scheme is one choice for the page and the stage.
- Until `src/core/options.css` is merged, the size, density, shape and tone classes are set but change nothing.

**Content.** Generic, as in 2.x: devices, tickets, "Product", Ada Lovelace. Never a real project, organisation,
place or brand (`test/repo.test.js`).

**Coverage.** Show every variant and the states (disabled, busy, error, empty), keyboard use and a narrow width. The
options panel applies size, density, shape, tone and theme around the demo, so the demo need not repeat them.
Every registered demo must render without console errors: `test/browser/styleguide-v3.spec.js` opens each one.

### Moving a 2.x section into `<n>.demo.js`

The 2.x sections live in `styleguide/styleguide.js` (rendered on `styleguide/legacy.html`). Charts is the worked
example: `src/components/chart/chart.demo.js` and `ported('charts', 'Charts', 'chart')` in `styleguide.js`.

1. Copy the section's markup function into `render(h)`.
   - Drop the outer `section(id, title, lead, …)`: the title becomes `title`, the lead becomes `lead`, and the
     one-line `need` is new.
   - Replace the styleguide helpers with `h.icon`, `h.card`, `h.esc`.
   - Turn fixed ids into `h.uid()`, or into `data-*` hooks that `wire` queries inside `root`.
2. Move the section's behaviour from `setupDemos()` and the `data-sg="…"` action router into `wire(root, h)`.
   - Keep only what a project would write.
   - Behaviour the system now owns (`data-ds-*`) goes away.
   - Timers use `h.slow(ms)`.
3. Take the shared helpers the section used (`fleet()`, `PEOPLE`, `statusChip()` …) along, as private functions of
   the demo file. Never reach into `styleguide.js`.
4. In `styleguide.js`, replace the section's function body with `ported('<id>', '<Title>', '<n>')`. Delete its
   setup and action code. legacy.html then shows the spec's markup in the old place, so its baseline screenshot
   still covers it. A section shared by several components moves when its last component does.
5. Run `npm run build` (it rewrites `styleguide/demos.js` and `styleguide/registry.js`).
6. Run `styleguide-v3.spec.js` and the 2.x specs of the section (`baseline`, `review`, `demos`,
   `styleguide-regressions`) with `DS_SHOTS=local`. A changed legacy screenshot is expected only where the markup
   changed: say so in the report.
7. Remove the section's entry from `LEGACY` in `styleguide/shell.js` once nothing links there.

The last step of phase 1 deletes `legacy.html`, `styleguide.js`'s 2.x sections, `LEGACY` and the specs' legacy paths.

## 8. Motion

- **Rules.** Every AGENTS.md motion rule holds: tokens only, the spring for movement that floats, `--ds-ease-out` for
  sizes, exits at 0.3-0.8 of their entrance, interrupted motion continues, hover never moves, and nothing scales on
  press except the switch handle.
- **Named exceptions.**
  - The D14 ones: chart path morph, tour spotlight glide, carousel slide.
  - The bottom sheet's drag.
  - Anything else needs a reason in `meta.json` `motionExceptions`, which the test allowlist reads, and a line in the
    report.
- **Motion Lab.** Every moving thing gets an entry in `<n>.lab.js`:
  `SG_LAB.add({ id, title, shows: ['keyframe', '.class', 'DS.x.fn', '--ds-token'], replay(root), toggle?(root, on) })`.
  The coverage test of `lab.spec.js` fails otherwise.

## 9. Shared files: what you may touch

- **Do not edit** (the integrator does it from your report):
  - `src/core/tokens.css`, `themes/*`, `scripts/tools/theme-rules.mjs`
  - `src/core/motion.css`, `scripts/build.mjs`
  - `package.json`, `CHANGELOG.md`, `README.md`, `AGENTS.md`
  - `dist/`, and any other component's folder
- **May append to:**
  - `src/js/core.js` `DEFAULT_STRINGS`, a key-value line per string
  - `src/js/icons.js`, a glyph only if truly missing, in the same style
  - `src/deprecations.json`, entries
- **Never commit `dist/`** on a group branch. If a test needs it, run `npm run build` locally and leave it uncommitted
  (`git checkout dist`) before committing.
- **CHANGELOG.** Write your lines at the end of your `<n>.md` under `<!-- changelog -->`, which the integrator moves.

## 10. Definition of done (per component)

1. CSS, `meta.json`, md, demo, spec, plus JS, unit test and lab entry when they apply, all to these conventions.
2. `npm run build && npm test` passes in your worktree. Then `git checkout dist` before committing.
3. Browser: your own spec, plus any 2.x spec of this component, pass in chromium, firefox and webkit, and the
   `fallback` project where the spec imports `base-test.js`.
   - Command: `DS_SHOTS=local DS_TEST_PORT=<your port> npx playwright test <specs> --project=chromium --project=firefox --project=webkit`.
   - Never run the whole suite; the machine is shared.
4. Forced colours checked (spec). Keyboard complete (spec). Names and roles checked (spec).
5. A port keeps every 2.x behaviour. Its 2.x browser specs pass unchanged in intent; an assertion may change only
   where the 3.0 API renamed something, and the report names each such change.
6. The report, at most 200 words: branch, commits, components done, renames, roles requested, strings added,
   motion exceptions, and anything left open.
